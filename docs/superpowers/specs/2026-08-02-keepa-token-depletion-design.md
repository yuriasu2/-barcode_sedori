# Keepa API トークン枯渇対応 設計書（v2）

作成: 2026-08-02 / ステータス: **設計承認済み（実装前）**

本書は旧 [KEEPA-TOKEN-PLAN.md](../../../KEEPA-TOKEN-PLAN.md)（2026-07-15、Render時代）の全面改訂版。
旧書の前提（Renderサーバー・旧無料枠・BYO無し）は現状と大きく乖離したため、
現アーキテクチャ（Cloudflare Workers + Durable Objects・フリーミアムv2・BYO Keepaキー）を
前提に作り直した。

## 0. 背景・現状（2026-08-02時点）

- サーバーは **Cloudflare Workers + Durable Objects**（`api.sellira.jp`）。共有の Keepa APIキーを
  1つ持ち、以下の利用者がその1つのトークンバケットを共有する:
  - 無料・SP-API未連携ユーザーの検索（`/api/search` Keepa経路）とグラフ（`/api/graph-data`）
  - Pro だが BYO Keepaキー未設定ユーザーのグラフ（SP-API未連携なら検索も）
- **共有バケットを消費しない者**: SP-API連携の検索（自分のAmazon枠）、BYO Keepaキー設定者
  （`X-Keepa-Key`。2026-08-02実装済み）、キャッシュヒット（検索30分・グラフ1時間）。
- **契約プラン**: 現在 5トークン/分（バケット上限300）。**20トークン/分へのアップグレードを予定**
  （Phase 0）。トークンは毎分連続的に補充され、未使用分はバケット上限までしか貯まらない。
- **現状の枯渇時挙動（要改善）**: Keepaクライアントが `keepa_tokens_exhausted` を投げ、
  サーバーは503を返す。iOSはこれを判別せず汎用エラーの生文言を表示する。
  グラフのみ「グラフを一時的に取得できません」＋タップ再試行が実装済み。
- **新たに判明した脅威**: デバイスID（`X-Device-Id`）は自己申告で検証されておらず、
  curl等でランダムIDを送るだけで無料枠が無限にリセットできることを本番で実証済み。
  共有バケットを枯らされると全ユーザーのグラフ・無料検索が壊れる。

## 1. 決定事項（ユーザー合意済み）

| 論点 | 決定 |
|---|---|
| 方式 | **有限の優先度付きキュー＋あふれ分は即お断り（load shedding）**。日次総量上限（ハードキャップ）は採用しない |
| Keepaプラン | 20トークン/分へアップグレード（Phase 0、ユーザー作業）。設計は5/分のままでも動作する |
| Pro優先 | **キュー内でProを常に無料より優先**する |
| お断り文言 | 「**混み合っているので時間を空けてお試しください。**」 |
| 根本の不正対策 | App Attest（別企画・Phase 3）。本設計のスコープ外 |

日次総量上限を採用しない理由: キューが消費速度を補充速度以下に自然に制限するため、
総量はKeepaの物理上限（補充率×24時間）を超えようがない。Keepaは定額契約であり
トークン超過課金も無いので、「総量を止める」装置は不要。必要なのは配分（Pro優先）と
枯渇時の体験改善であり、それはキュー＋sheddingが担う。

## 2. 設計

### 2.1 KeepaThrottleDO（新規 Durable Object）

共有Keepaキーの「トークン残量の推定」と「優先度付き待ち行列」を一元管理する
グローバルに1つのDO。`deviceQuota.js` / `quotaDurableObject.js` と同じ実装作法に揃える:

- Workers本番: `globalThis.__keepaThrottleDO`（worker.jsがバインディングを橋渡し）経由で委譲
- Node/テスト: DOバインディングが無い場合はインメモリ実装へフォールバック
- 公開APIはasync、戻り値の形はDO経路とインメモリ経路で同一

**トークン残量の推定**: 容量 = `KEEPA_REFILL_PER_MIN × 60`（20/分なら1,200）、
補充は時刻差から連続的に計算（20/分なら3秒に1トークン）。Keepaレスポンスに毎回入る
`tokensLeft` で推定値を都度補正する（呼び出し元が消費後に `report(tokensLeft)` を返す）。
Keepaが `keepa_tokens_exhausted`（503）を返したら残量0へ補正する。
このとき当該リクエスト自体は再試行せず、キュー拒否と同じ `keepa_busy`（429・同文言）で
返す（ユーザーから見た体験を1種類に揃える。推定補正済みなので直後のリクエストは正しく並ぶ）。

**acquire(priority) の挙動**:

1. 推定残量 ≥ 1 → 即時許可（残量をデクリメント）。通常時のオーバーヘッドはDOへの1往復のみ
2. 残量 0 → キューへ。**Proは常に無料より先頭側**（優先度2値の単純な2本キュー）
3. キュー深さが `KEEPA_QUEUE_DEPTH`（既定10）に達していたら**enqueueせず即座に拒否**
4. 待ち時間が `KEEPA_QUEUE_TIMEOUT_MS`（既定8,000ms）を超えたら**タイムアウトで拒否**
5. 補充ペースに合わせて（DOのalarmで）キュー先頭から順に許可

拒否（3・4）はどちらも同じレスポンス: **HTTP 429** `{ error: "keepa_busy",
message: "混み合っているので時間を空けてお試しください。" }`。
既存の `quota_exceeded`（429）とは `error` コードで区別する。

**DO障害時の方針**: deviceQuotaと同じく**許可で倒す**（可用性優先）。スロットルが一時的に
効かなくなるリスクより、正当なユーザーが使えなくなる実害の方が大きい。console.errorでログは残す。

### 2.2 適用範囲

| 経路 | キュー適用 |
|---|---|
| `/api/search` Keepa経路・キャッシュミス | **する**（無料枠ユニット消費判定の後・Keepa呼び出しの直前） |
| `/api/graph-data` キャッシュミス | **する** |
| 上記のキャッシュヒット | しない（Keepaを呼ばない） |
| SP-API連携の検索 | しない（自分のAmazon枠） |
| BYO Keepaキー（`X-Keepa-Key`）でのKeepa呼び出し | しない（自分のKeepa枠。混雑の巻き添えにしない） |
| `/api/keepa-test` | しない（`/token` はトークンを消費しない） |

無料枠ユニットの消費順序に注意: **ユニットを消費した後にキュー拒否が起きるとユニットだけ
失われる**。実装では「キュー許可を得てからユニットを消費する」順に並べ替えるか、
拒否時にユニットを返却する。どちらにするかは実装計画で決めるが、ユーザーが
「エラーになったのに枠だけ減った」状態を作らないことを受け入れ条件とする。

### 2.3 iOS側の変更

- `APIClientError` に `keepaBusy` 相当の判別を追加（429 + `error: "keepa_busy"`）。
  既存の `quotaExceeded`（429 + `quota_exceeded`）の判別と同居させる
- 検索失敗時: 検索カード位置に「混み合っているので時間を空けてお試しください。」＋
  **再試行ボタン**（スキャンし直さず同じコードで再検索）
- あわせて誘導を添える（混雑を連携・課金の入口に変える。旧企画書の思想を継承）:
  - SP-API未連携: 「Amazon連携なら自分の枠で待たずに検索できます」→ 設定タブへ
  - Pro・BYO未設定: 「Keepa APIキー設定でグラフも自分の枠に」→ 設定タブへ
- グラフ失敗時: 既存の失敗表示（タップ再試行）を流用し、`keepa_busy` のときだけ
  文言を「混み合っているので時間を空けてお試しください。」に出し分け

### 2.4 監視（ログのみ・YAGNI）

KeepaThrottleDOが日次統計を保持し、変化時に構造化ログへ出す（`wrangler tail` で確認）:
許可数 / 待ち発生数 / 破棄数（深さ超過・タイムアウト別）/ 直近のtokensLeft。
ダッシュボード・アラート・管理APIは作らない。破棄数が恒常的に増えたらプラン増強か
App Attest前倒しの判断材料にする。

### 2.5 環境変数（wrangler.jsonc vars）

| 変数 | 既定 | 意味 |
|---|---|---|
| `KEEPA_REFILL_PER_MIN` | `5` | 契約プランの毎分トークン数。プラン変更時にここだけ更新 |
| `KEEPA_QUEUE_DEPTH` | `10` | キュー深さ上限（超過分は即拒否） |
| `KEEPA_QUEUE_TIMEOUT_MS` | `8000` | キュー待ちの最大時間。iOSの通信タイムアウトより短くすること |

## 3. フェーズ

- **Phase 0（ユーザー作業）**: Keepaプランを20トークン/分へアップグレード。
  完了後 `KEEPA_REFILL_PER_MIN=20` に変更してデプロイ
- **Phase 1（今回実装）**: 2章の全て（KeepaThrottleDO＋shedding＋iOS表示＋監視ログ）
- **Phase 2（実装済み・記録）**: 消費の根本削減策は実装済み — 検索30分/グラフ1時間キャッシュ、
  検索時のグラフ先入れ、SP-API連携（BYO）、BYO Keepaキー、SP-API連携者のグラフ取得5秒静止待ち
- **Phase 3（将来・別企画書）**: App Attestによる不正リクエスト遮断。
  デバイスID自己申告の穴（無料枠リセット・キュー占拠）の根本対策

## 5. リスクと限界

- **curl等の大量アクセスはキューを満杯にし続けられる**。被害は「混雑表示が続く」まで
  （消費速度は補充速度を超えない）。根本対策はPhase 3のApp Attest
- **Pro優先は `X-App-Plan` 自己申告に依存**（偽装可能）。同上、App Attestで塞ぐ
- 混雑時に無料ユーザーが後回しになるのは意図した挙動
- キュー待機中はWorkerがHTTPリクエストを最大8秒保持する。Workersの実行モデル上
  問題ない（CPU時間ではなく壁時計時間）。iOS側のURLSessionタイムアウトがこれより
  長いことは確認済み(iOS=10秒 > キュー待ち8秒)
- 推定残量とKeepa実残量のズレは `tokensLeft` 補正で収束するが、複数リクエストの
  並行消費で一時的に過小/過大になり得る。過大側はKeepaの503を残量0補正で吸収する

## 6. テスト方針

- サーバー: インメモリフォールバック経路でユニットテスト（即時許可 / Pro優先順 /
  深さ超過拒否 / タイムアウト拒否 / tokensLeft補正 / ユニット消費との順序）。
  既存 `server/test/` の作法（node --test、fetchモック）に揃える
- iOS: `keepa_busy` 判別のデコード確認と、シミュレータでの表示確認
  （サーバーの環境変数を極端な値にした検証は行わず、モック/一時コードで表示のみ確認）
