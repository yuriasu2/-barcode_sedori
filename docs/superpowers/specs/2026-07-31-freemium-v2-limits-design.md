# フリーミアム v2: プラン制限・リワード広告 設計書

- 作成日: 2026-07-31
- ステータス: 確定（実装前）
- 関連文書: `FREEMIUM-PLAN.md`（旧設計・本書が制限まわりを置き換える）、`docs/superpowers/specs/2026-07-30-server-managed-ads-design.md`
- スコープ外: **Keepaトークン枯渇時の制御は別文書「Keepa API トークン枯渇 対応 企画書」の管轄**であり、本書では扱わない

## 1. 背景と目的

現行の無料プランは 1日100回（クライアント）/150回（サーバー）までKeepa経路の検索を許しており、無料ユーザーが増えるとKeepaトークンが枯渇し、Pro含む全ユーザーの検索が止まるリスクがある。本設計では:

1. **コスト保護**: 無料ユーザーによるKeepaトークン消費に低い上限を設ける
2. **Pro転換**: 上限到達時に最も転換率が高いペイウォールを出す
3. **収益化**: リワード広告で無料ヘビーユーザーを収益源に変える
4. **連携誘導**: SP-API連携（=運営コストゼロ経路）へ誘導する

## 2. プラン別機能マトリクス（確定仕様）

| 機能 | 無料・未連携 | 無料・連携済み | Pro |
|---|---|---|---|
| バーコードスキャン | 基本5回/日 + 広告で+5回（日次合計100回上限） | **無制限**（SP-API経路・トークン消費0） | 無制限 |
| OCRスキャン | 基本5回枠内のみ（広告枠では不可） | 基本5回枠内のみ | 無制限 |
| 手入力検索 | スキャンと同じ枠を消費 | 無制限（SP-API経路） | 無制限 |
| 価格（第1段階） | スキャンと同時表示 | 表示 | 表示 |
| オファー一覧 | ✕（ロック表示→連携誘導） | ○（SP-API同梱） | ○（SP-API連携必須） |
| 価格グラフ | スキャン枠に同梱（追加消費なし） | 枠1消費/商品 + 広告で+5回 | 無制限 |
| 出品・仕入れ | ✕ | ✕ | ○（SP-API連携必須） |
| 利益アラート | ✕ | ✕ | ○ |
| バナー広告 | あり | あり（グラフ枠等） | なし |
| スキャンクールダウン | 5秒 | 5秒 | 1秒 |

- OCR検索は**JANコード読み取り→コード検索**（キーワード検索ではない）ため、Keepa経路でもバーコードと同じ1トークン。枠の重み付けは不要。
- 広告視聴の上限: 日次合計枠が100に達するまで（基本5 + 広告19本×5 = 100）。**100到達後はPro/連携の2択**になり広告選択肢は消える。

## 3. 中核概念: 無料枠ユニット（サーバー権威）

複数のカウンタを持たず、**「そのデバイスのために今日消費したKeepaトークン数 ≒ ユニット」** をサーバーで一元管理する。

### 3.1 消費ルール

| 操作 | ユニット消費 |
|---|---|
| 未連携の検索（バーコード/OCR/手入力）で**Keepa実フェッチが発生** | 1 |
| 同上でコードを識別子に変換できず**Keepaを呼ばない**（`unresolved` / `no_identifier`） | 0 |
| 同上で**サーバーキャッシュ命中**（30分TTL） | 0 |
| 連携済みの検索（SP-API経路） | 0（無制限） |
| グラフデータ取得で**Keepa実フェッチが発生** | 1 |
| グラフデータ取得で**キャッシュ命中**（1時間TTL） | 0 |
| Pro のあらゆる操作 | 0（カウント対象外） |

- 未連携の検索は `history:1` でグラフ生データを `graphDataCache` に先入れする現行実装（`server/src/routes.js:518-521`）により、**検索直後のグラフ表示は0消費**。「未連携はスキャン5回にグラフ込み」が追加実装なしで成立する。
- 同一商品グラフの再表示はキャッシュTTL（1時間）内なら0消費。TTL切れ後の再表示は1消費する（商品単位の厳密な解禁管理はしない。稀なケースでありYAGNI）。

### 3.2 付与ルール

```
日次ユニット上限 = BASE_DAILY_UNITS(5) + UNITS_PER_AD(5) × 当日のSSV検証済み広告視聴数
ただし MAX_DAILY_UNITS(100) を超えない（広告は実質19本/日まで）
```

### 3.3 OCRの追加制約（クライアントゲート）

- OCRは**基本枠（5回/日）内のみ**。広告で増えた枠では使えない。連携済みでも同じ。
- サーバーはOCR由来かどうか判別できないため、この制約は**クライアント側でエンフォース**する（現行 `ScanQuotaStore.freeOcrDailyLimit` の仕組みを 3→5 に変更して流用）。
- 改ざんされた場合の実害: 未連携ならユニットは正しく消費される（コスト保護は保たれる）。連携済みはコスト0。いずれも許容範囲。

## 4. サーバー設計

### 4.0 旧クライアント互換について（実装中に撤回した判断）

実装当初は「新上限100が旧クライアントのバックストップとして機能する」という前提が誤りだったため、`X-Quota-Model: v2` ヘッダーによるオプトイン方式（v2非対応の旧クライアントには `deviceRateLimit.js` のレガシー150回/日を残す）を一度実装した。

その後、**このアプリはまだApp Storeに公開されておらず、TestFlight等の既存利用者もいない**ことを確認した。守るべき旧クライアントが存在しないため、このオプトイン方式・レガシー経路一式（`isQuotaV2Request`、`deviceRateLimit.js`、`FREE_DEVICE_DAILY_LIMIT`）は不要な複雑さと判断し、**すべて撤去した**。

現在の実装は単純に「Pro=無制限、非Pro=常に無料枠ユニットモデル」のみ。`/api/graph-data` も無条件で無料開放している（キャッシュヒットは消費なし、ミス時のみユニット消費）。

将来また互換性が必要になる場面（例: サーバー側の制限モデルを再び変更する際に旧アプリが残っている）があれば、その時点で同様のヘッダーオプトイン方式を再導入すればよい。

### 4.1 定数（`server/src/routes.js` / `wrangler.jsonc`）

| 定数 | 値 | 備考 |
|---|---|---|
| `BASE_DAILY_UNITS` | 5 | 現行 `FREE_DEVICE_DAILY_LIMIT=150` を置き換え |
| `UNITS_PER_AD` | 5 | |
| `MAX_DAILY_UNITS` | 100 | 広告込みの日次ハードキャップ |

### 4.2 デバイスクォータ（`deviceRateLimit.js` を拡張 → `deviceQuota.js`）

- 現行の `Map<deviceId, {date, count}>`（`server/src/deviceRateLimit.js:23`）を `{date, unitsUsed, adGrants}` に拡張。
- 日付境界は現行踏襲でUTC。インメモリのままとする（Workers isolate分散・再起動リセットの弱さは現行と同等の「バックストップ」設計として許容。厳密化が必要になったらKV/Durable Objects移行を検討）。
- クライアント側にも同じ制限を実装するため、正直なクライアントはクライアント側で先に止まる（現行と同じ二重構え）。

### 4.3 エンドポイント変更

**`GET /api/search`**（`server/src/routes.js:581`）
- 未連携（SP-API資格情報なし）かつ非Pro: Keepaフェッチ前にユニット残を確認。不足なら **HTTP 429 `quota_exceeded`**。レスポンスに `quota` オブジェクト（後述）を含める。
- キャッシュ命中時は消費しない（判定はフェッチ直前ではなくフェッチ実行時に行う）。
- 連携済み（SP-API経路）: ユニット消費なし・無制限（現行どおり通過）。

**`GET /api/graph-data`**（`server/src/routes.js:814`）
- 現行の Pro 403 ゲート（`routes.js:821-823`）を撤去し、**無料にも開放**。ただし非Proはユニット消費の対象:
  - キャッシュ命中 → 0消費で返す
  - キャッシュミス → ユニット残があれば1消費してKeepaフェッチ、なければ **429 `quota_exceeded`**
- `/api/graph`（画像版・未使用）は現行のProゲートのまま据え置き。

**`GET /api/quota`（新設）**
- リクエスト: `X-Device-Id` ヘッダー
- レスポンス:
```json
{
  "unitsRemaining": 3,
  "baseRemaining": 3,
  "adGrantsToday": 0,
  "adAvailable": true,
  "capReached": false
}
```
- `adAvailable`: `unitsUsed + UNITS_PER_AD <= MAX_DAILY_UNITS` かどうか。
- `/api/search`・`/api/graph-data` の応答（成功・429とも）にも同じ `quota` オブジェクトを同梱し、クライアントの残数表示を常に最新化する。

**`GET /api/admob/ssv`（新設）** — リワード広告のサーバーサイド検証
- AdMob管理画面にこのURLをSSVコールバックとして設定。Googleのサーバーから `?ad_network=...&reward_amount=...&custom_data=<deviceId>&signature=...&key_id=...` 形式のGETが届く。
- 検証: `https://www.gstatic.com/admob/reward/verifier-keys.json` の公開鍵（key_idで選択、キャッシュ可）でECDSA署名を検証。
- 検証OK → `custom_data` のdeviceIdについて `adGrants += 1`（上限: `(MAX_DAILY_UNITS - BASE_DAILY_UNITS) / UNITS_PER_AD = 19`）。200を返す。
- 検証NG → 400。付与しない。
- これにより「クライアントの自己申告で+5」を排除する（動画を見ずに報酬を得る改ざんの対策）。

### 4.4 トークン枯渇時の挙動

- Keepaトークン枯渇時の制御（優先度・拒否・リトライ等）は別文書「Keepa API トークン枯渇 対応 企画書」の管轄。本設計では現行の挙動（枯渇時に503へマップ）を変更しない。

### 4.5 Pro判定に関する注記

- Pro判定は現行どおり自己申告の `X-App-Plan` ヘッダー（`server/src/routes.js:71-74`）。レシート検証（App Store Server API）は既存コメントどおり別フェーズの課題であり、本設計のスコープ外。偽装すれば無料制限を回避できる既知リスクは残る。

## 5. iOS設計

### 5.1 ScanQuotaStore の変更（`ios/.../Store/ScanQuotaStore.swift`）

- `freeDailyLimit: 100 → 5`（基本枠）
- `freeOcrDailyLimit: 3 → 5`（基本枠と同数。OCR使用は基本枠と両方を消費）
- 追加: サーバー `/api/quota` の残数ミラー（`unitsRemaining`, `adAvailable`, `capReached`）。表示と即時判定はローカル値、権威はサーバー応答で常に上書き。
- 広告付与分はローカルで勝手に加算しない。SSV到達後のサーバー応答が唯一の加算経路。

### 5.2 スキャン画面（`ios/.../Views/SearchTabView.swift`）

**枠切れ時の挙動（未連携）**
1. 5回目のスキャン完了 → **結果カードは表示したまま**、`isScannerActive = false` でカメラ停止。
2. カメラ領域にペイウォールオーバーレイを重ねる（背景: カメラ最終フレームの暗転 or 単色）:
   - **① Proにアップグレード — スキャン・OCR・グラフすべて無制限**（最上段・強調）
   - ② 動画を見て+5回スキャン（リワード広告。`adAvailable == false` なら非表示）
   - ③ Amazon連携（大口セラー）でバーコードスキャン無制限
3. OCRモード中に枠切れした場合: `scanMode = .barcode` に**強制切替してから**オーバーレイを表示。
4. 以後OCRボタンをタップしたら、モードは切り替えずポップアップ:「OCR機能を無制限に使うにはProにアップグレードしてください。」
5. 日次100回到達後（`capReached`）: 選択肢②を消し **①Pro / ③連携 の2択**。

**広告視聴後**
- `onUserEarnedReward` を受けたら即付与せず、`/api/quota` をポーリング（1秒間隔・最大10秒）して残数が増えたのを確認してからカメラを再開。SSV遅延中は「反映中…」表示。
- タイムアウトした場合は「反映に時間がかかっています。しばらくしてからお試しください」を表示（付与はサーバー到達時に自動反映）。

**連携済み**
- バーコードは無制限のためカメラは常時アクティブ。ペイウォールオーバーレイは出さない。
- OCRボタンはOCR残0でロック（鍵アイコン、現行 `SearchTabView.swift:399-405` の仕組みを流用）。タップでPro訴求ポップアップ。

**手入力検索のゲート修正（既存バグ）**
- `submitSearchBarText()`（`SearchTabView.swift:375-392`）が `ScanQuotaStore` を通らず枠を迂回している。スキャンと同一のゲート（`registerScanIfAllowed()`）を通す。連携済みは通過。

### 5.3 グラフ枠の状態分岐（`SearchTabView.swift:213-217` の分岐を刷新）

| 状態 | 表示 |
|---|---|
| Pro | `keepaGraph`（現行どおり） |
| 無料・ユニット残あり | グラフ表示（`/api/graph-data`。検索直後はキャッシュ命中で0消費） |
| 無料・ユニット切れ | バナー広告（`search_ad` スロット） + 「動画を見てグラフを見る（+5回）」ボタン + Pro訴求リンク |
| 無料・`capReached` | バナー広告 + Pro訴求のみ |

- 「グラフ+5回」と「スキャン+5回」は同一ユニットの付与であり、ボタンの文言だけ文脈で変える（未連携はスキャン訴求、連携済みはグラフ訴求）。

### 5.4 リワード広告（新規 `ios/.../Ads/RewardedAdManager.swift`）

- `GADRewardedAd` をロード・表示するシングルトン。表示前に `serverSideVerificationOptions.customRewardString = deviceId` を設定。
- ロード失敗・在庫なし時はボタンを無効化し「広告を準備できませんでした。しばらくしてからお試しください」。
- Pro購入済みユーザーには一切表示しない（既存の `isVisible(isPro:)` ポリシーと同じ）。

### 5.5 ペイウォール文言（`ios/.../Views/PaywallView.swift`）

- 訴求リストの「スキャン上限なし」等を新制限（1日5回）前提の文言に更新。
- OCR・グラフ無制限、広告なし、クールダウン1秒、出品・仕入れ・アラートを列挙（現行リストの更新）。

## 7. 既知の制約・スコープ外

1. **Pro判定は自己申告**（`X-App-Plan`）。レシート検証は別フェーズ。
2. **デバイスクォータはインメモリ**。Workers isolate分散・再起動でリセットされうる。バックストップ設計として許容し、必要になればKV/Durable Objects化。
3. **deviceIdは自己申告**。再インストール等でリセット可能。厳密化はレシート検証と合わせて将来対応。
4. **AdMob App IDがテスト値**（`Generated/Info.plist:35`）、**StoreKit productIDがプレースホルダ**（`EntitlementStore.swift:16`）。リリース前に本番値へ差し替え（本設計とは別トラックの既知課題）。

## 8. 移行・告知・審査

- 既存無料ユーザーは実質 100回/日 → 5回/日+広告 への大幅変更。**初回起動時に変更告知モーダル**を表示し、リリースノートにも明記する。
- App Store審査: リワード広告による機能解放はガイドライン上問題なし（IAP迂回と誤認されないよう「時間限定の追加回数」であることを文言で明確化）。審査員は大口セラー連携を持たないため、無料フロー＋Pro購入（Sandbox）で全機能確認可能な状態を保つ。`debugForcePro` はDEBUGビルド限定で維持。

## 9. 実装フェーズ

| フェーズ | 内容 | 依存 |
|---|---|---|
| **A. サーバー** | ユニットモデル（`deviceQuota.js`）、`/api/search` 429化、`/api/graph-data` 無料開放、`/api/quota` 新設 | なし。広告なしでも成立 |
| **B. iOS 制限まわり** | ScanQuotaStore改修、ペイウォールオーバーレイ（3択/2択）、OCR強制切替・ポップアップ、手入力ゲート修正、グラフ枠分岐 | A |
| **C. リワード広告** | RewardedAdManager、SSVエンドポイント、AdMob管理画面設定、反映ポーリング | A, B |

- 既存利用者がいないため互換レイヤーは不要（4.0参照）。サーバーは常に無料枠ユニットモデルを適用する。iOS側もヘッダーの出し分けは不要。
- サーバーは手動デプロイ（push では反映されない）。A完了後にデプロイしてからBへ進む。
